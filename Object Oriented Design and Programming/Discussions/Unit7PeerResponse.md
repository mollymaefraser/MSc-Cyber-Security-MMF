Good catch on the SQL injection point, that's exactly the same observation I made in my own post: the code does a direct Python string comparison, so there is no query for the payload to actually inject into. It is reassuring to see two people independently spot that the vulnerability is more illustrative than literal in this specific implementation. Your point about parameterised queries is the right follow up though, since that is the actual fix once a real database and dynamically built query enter the picture, rather than just hashing or validating harder on the Python side.

I like that you separated "trusting input too easily" as the general theme rather than treating each vulnerability as an isolated fix. It is a good framing, since password hashing, input validation, and rate limiting all really are instances of the same underlying principle: never assume what arrives at a function is safe just because it came from a login form rather than somewhere more obviously hostile.

Your citations around designing for security from the start rather than patching afterwards match something I have seen argued elsewhere too, that retrofitting security tends to be more expensive and less thorough than building it in from the first version. Do Shah and Baker go into what that looks like practically for a small team, or is it more of a general principle in their argument? I ask because it is one thing to say "think about security early" and another to say concretely what that means when you are the only developer on a small project like this one, where a full threat model might be overkill.

One thing I would push on: you mention rate limiting restricting repeated failed attempts, but did you consider whether that should be scoped per username, per IP address, or both? Per username alone lets an attacker lock a legitimate user out of their own account, which is its own denial of service angle worth thinking about.

Thanks for sharing these — it's helpful seeing different real-world framings for the same patterns.

Your Adapter example is a nice contrast to mine: I went with SOAP/REST specifically to highlight a protocol-level mismatch, but your version showing a mismatch in method names/signatures (`submit_transaction()` vs `pay()`) is actually the more common case in practice — most legacy integrations aren't a different protocol, just a different vocabulary. One thing I'd add: did you consider having `PaymentAdapter` implement a shared interface (like my `PaymentGateway` ABC)? Without it, `PaymentAdapter` technically works, but the client code has no guarantee it can swap in a different gateway later without knowing `PaymentAdapter`'s specific method name — the abstract interface is what actually buys you the decoupling, not just the adapter class itself.

Your Bridge example is cleaner than mine in one respect — you're not distinguishing "Basic" vs "Advanced" remotes, just one `Remote` class working with any device. That's arguably purer Bridge, since my `AdvancedRemoteControl` subclass is technically extending the abstraction hierarchy, which starts to reintroduce some of the coupling Bridge is meant to avoid. Did you consider how you'd add remote-specific behaviour (like an advanced remote's extra buttons) without either subclassing `Remote` or bloating `Device`?

Your Composite example maps well to a real scenario I hadn't considered — I like that "browsing as one structure" framing more than my file-system example, since it's a bit more relatable. One question: your `show()` on `Folder` returns a nested list of names rather than printing indented output like mine — do you think that's a meaningful design choice (e.g. keeping `show()` pure/data-returning rather than side-effecting with `print()`), or just a simpler way to demo the concept?

Good post! I like that you didn't just present Strategy as an unconditional win. That closing point about a 2-3 payment-type system not justifying the extra classes is something a lot of posts (mine included, if I'm honest) gloss over. It's a useful reminder that OCP compliance isn't free and that it's a trade against added indirection, and the trade only pays off once change is actually likely.

`set_strategy()` is a nice addition too. My own version passed the strategy into `__init__` only, which quietly assumes a `PaymentProcessor` is single-use per checkout. Your point about a customer switching from card to PayPal mid-checkout is a much more realistic scenario (one that I myself have done before), and it highlights something Strategy gives you almost for free: the context object can be reconfigured at runtime without being torn down and rebuilt, which a rigid if-elif version can't offer nearly as cleanly.

One thing I'd push on: since `set_strategy()` allows the strategy to be swapped at any time, is there a risk of it being changed mid-transaction — e.g. if `process_payment()` were ever made asynchronous, or if some future validation step ran between selecting a strategy and calling `pay()`? Right now it's safe because everything happens synchronously in sequence, but I'd be curious whether you'd consider locking the strategy once processing starts, or whether that's over-engineering for a case that doesn't apply here yet.

Also, nice use of Nesteruk and Sarcar to back up the OCP violation point with more than just the code itself. Sarcar's observation about the same problem recurring in a Java payment example is a good way to show this isn't a Python-specific quirk, it's a general OOP design issue.
